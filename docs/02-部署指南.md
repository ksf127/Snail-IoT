# 02 · 部署指南

> 本文描述 Snail-IoT 的两种部署方式：① Docker Compose 编排（第 1–9 节）；② Kubernetes（Docker Desktop 内置 k8s）+ Jenkins / GitHub Actions 自动化流水线（第 10–12 节）。
> 配套可视化图表见 [diagrams/02-部署拓扑图.html](file:///d:/DevProjects/snail/docs/diagrams/02-部署拓扑图.html)。

---

## 1. 部署架构总览

部署分为两层 Compose 编排：

| 编排文件 | 位置 | 职责 | 网络 |
| --- | --- | --- | --- |
| 根编排 | [docker-compose.yml](file:///d:/DevProjects/snail/docker-compose.yml) | 基础设施：PostgreSQL(pgvector) + Redis | 未声明 `networks`，按 Compose 项目名创建默认网络 |
| 业务编排 | [iot-platform/script/docker/docker-compose.yml](file:///d:/DevProjects/snail/iot-platform/script/docker/docker-compose.yml) | Nacos/ES/Kafka/EMQX/MinIO/后端/SBA/SnailJob/SnailAI/前端 | 复用外部网络 `devprojects_default` |

**为什么分两层**：基础设施生命周期长、数据需持久化；业务容器迭代频繁。分层后业务容器可独立重建而不影响数据。

### 1.1 网络名约定（重要）

根编排没有显式声明 `networks`，Compose 会用“项目名 + `_default`”创建默认网络。仓库目录名为 `snail`，因此默认会得到 `snail_default`；而业务编排硬编码复用 `devprojects_default`，二者不一致会报：

```
network devprojects_default declared as external, but could not be found
```

解决办法是让根编排的项目名固定为 `devprojects`：

```bash
# 方式一：命令行显式指定（推荐）
docker compose -p devprojects -f docker-compose.yml up -d

# 方式二：环境变量（PowerShell）
$env:COMPOSE_PROJECT_NAME='devprojects'
docker compose -f docker-compose.yml up -d
```

> 业务编排也建议带 `-p devprojects`，保持容器名与网络一致；若使用 `docker compose -p devprojects -f script/docker/docker-compose.yml`，其外部网络引用仍然成立。

### 1.2 统一入口

前端镜像内置 [nginx.conf](file:///d:/DevProjects/snail/iot-platform/plus-ui/nginx.conf)，`iot-web` 的 **80 端口是唯一对外入口**：

| 路径 | 上游 |
| --- | --- |
| `/prod-api/` | `iot-server:8080`（去前缀） |
| `/admin/` | `iot-sba:9090` |
| `/snail-job/` | `iot-snailjob:8800` |
| `/snail-ai/` | `iot-snailai:8900` |
| `/jenkins-api/` | `host.docker.internal:8090`（Nginx 注入 Basic 认证） |

1. **JDK 21** + **Maven 3.9+**（构建后端）
2. **Node.js ≥ 20.19** + **pnpm ≥ 10**（本机构建前端，或使用容器内多阶段构建）

## 4. Compose 部署步骤

### 步骤 1：启动基础设施

```bash
cd d:/DevProjects/snail
docker compose -p devprojects -f docker-compose.yml up -d
```

此步创建 `devprojects_default` 网络，并启动 `ruoyi-postgres`、`ruoyi-redis`。`init-vector.sql` 会在数据库首次初始化时执行（创建 pgvector 扩展等）。

验证：

```bash
docker ps --filter name=ruoyi-postgres --filter name=ruoyi-redis
```

### 步骤 2：构建并安装框架底座

产品 `iot-platform` 继承 `org.dromara:iot-vue-plus:6.0.0` 作为父 POM，**必须先将框架安装到本地 Maven 仓库**：

```bash
cd d:/DevProjects/snail/thirdparty/iot-vue-plus
mvn -DskipTests clean install
```

### 步骤 3：构建产品后端

```bash
cd d:/DevProjects/snail/iot-platform
mvn -Pprod -DskipTests clean package
```

产出：`iot-platform-admin/target/iot-platform-admin.jar`。

> `-Pprod` 激活生产打包；`iot-server` 容器以 `SPRING_PROFILES_ACTIVE=prod` 运行。

### 步骤 4：启动业务编排

```bash
cd d:/DevProjects/snail/iot-platform
docker compose -p devprojects -f script/docker/docker-compose.yml up -d --build
```

首次构建会编译以下镜像：

| 镜像 | 构建上下文 |
| --- | --- |
| `iot-platform/iot-platform-admin:1.0.0` | `iot-platform-admin` |
| `iot-platform/monitor-admin:6.0.0` | `thirdparty/iot-vue-plus/iot-extend/iot-monitor-admin` |
| `iot-platform/snailjob-server:2.0.2` | `thirdparty/iot-vue-plus/iot-extend/iot-snailjob-server` |
| `iot-platform/snailai-server:1.1.1` | `thirdparty/iot-vue-plus/iot-extend/iot-snailai-server` |
| `iot-platform/plus-ui:1.0.0` | `plus-ui` |

### 步骤 5：验证

```bash
docker compose -p devprojects -f script/docker/docker-compose.yml ps
```

访问 **http://localhost** → 登录页 → `admin / admin123` 登录成功即部署完成。

## 5. 启动顺序与依赖

```
postgres / redis (根编排)
        │
        ▼
nacos ─ elasticsearch ─ kafka ─ emqx ─ minio ─ minio-init
        │(healthcheck)
        ▼
   iot-server ──depends_on──▶ elasticsearch(healthy), kafka(healthy)
        │
        ├─▶ iot-sba ──▶ iot-snailjob
        │           └─▶ iot-snailai
        ▼
     iot-web (depends_on: iot-server, iot-sba, iot-snailjob, iot-snailai)
```

**关键依赖**：

- `iot-server` 等待 `elasticsearch` 与 `kafka` 健康后才启动；
- `iot-snailjob` / `iot-snailai` 依赖 `iot-sba` 完成注册；
- `iot-web` 等待 4 个后端容器启动（Nginx 的 upstream 在启动时解析 DNS）。

## 6. 环境变量与 Profile

`iot-server` 的生产配置由 [application-prod.yml](file:///d:/DevProjects/snail/iot-platform/iot-platform-admin/src/main/resources/application-prod.yml) 读取环境变量，业务编排已预置：

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | `prod` | 激活生产配置 |
| `POSTGRES_HOST` | `ruoyi-postgres` | 复用根编排容器 |
| `POSTGRES_DB` / `POSTGRES_USERNAME` / `POSTGRES_PASSWORD` | `ruoyi` / `postgres` / `postgres` | 数据库 |
| `REDIS_HOST` / `REDIS_PASSWORD` | `ruoyi-redis` / `123456` | 缓存 |
| `ES_HOST` / `ES_PORT` / `EASY_ES_ENABLE` | `iot-elasticsearch` / `9200` / `true` | 搜索引擎 |
| `KAFKA_SERVERS` | `iot-kafka:9092` | 消息队列（容器内） |
| `MQTT_HOST` / `MQTT_PORT` / `MQTT_CLIENT_ENABLED` | `iot-emqx` / `1883` / `true` | MQTT |
| `SBA_HOST` / `SBA_PORT` | `iot-sba` / `9090` | 监控中心注册 |
| `SNAILJOB_HOST` | `iot-snailjob` | 调度中心 |
| `SNAILAI_HOST` | `iot-snailai` | AI 服务 |
| `GITHUB_TOKEN` | 空 | 配置后可同步私有仓库 |

### 6.1 dev 与 prod 配置差异

| 配置项 | dev（`application-dev.yml`） | prod（`application-prod.yml`） |
| --- | --- | --- |
| 数据源 | `jdbc:postgresql://localhost:5432/ruoyi`，`postgres/postgres` | `${POSTGRES_*}` 环境变量 |
| Redis | `localhost:6379`，**无密码** | `${REDIS_*}`，默认密码 `123456` |
| SBA | 关闭 | 开启，`${SBA_HOST}:${SBA_PORT}/admin` |
| SnailJob | 关闭 | 开启 |
| SnailAI | 开启，`app-id: iot-vue-plus-001` | 开启，`app-id: 1` |
| Easy-ES | 默认关闭（`easy-es.enable=false`） | `${EASY_ES_ENABLE:false}` |
| MQTT 客户端 | 默认关闭 | `${MQTT_CLIENT_ENABLED:false}` |
| SQL 日志 | 开启 | 关闭 |
| 上传临时目录 | 系统默认 | `/ruoyi/server/temp` |

> **本地 dev 直连注意**：根编排的 Redis 带 `--requirepass 123456`，而 dev profile 未配置密码。若在本机以 `dev` 启动后端并连接根编排 Redis，需要显式设置 `REDIS_PASSWORD=123456`（或在 `application-dev.yml` 中补密码）。

### 6.2 GitHub Token

在【自动化部署 → GitHub 项目】页同步仓库时：

- **未配置 Token**：走 `/users/{owner}/repos`，只能拿到公开仓库；
- **配置 Token**：走 `/user/repos?affiliation=owner&visibility=all` 并携带 `Authorization: Bearer`，可同步该账号的私有仓库。

Token 生成入口：GitHub → Settings → Developer settings → Personal access tokens（classic 勾选 `repo`；fine-grained 授予目标仓库 `Contents: Read`）。

K8s 环境写入 `script/k8s/secret.yaml` 的 `GITHUB_TOKEN`（或 `kubectl patch secret`）后重启 `iot-server` 生效。

## 7. 日常运维命令

```bash
# 启动全部（含重建镜像）
docker compose -p devprojects -f script/docker/docker-compose.yml up -d --build

# 停止（保留数据卷）
docker compose -p devprojects -f script/docker/docker-compose.yml down

# 停止并删除数据卷（谨慎）
docker compose -p devprojects -f script/docker/docker-compose.yml down -v

# 查看状态
docker compose -p devprojects -f script/docker/docker-compose.yml ps

# 查看某服务日志
docker compose -p devprojects -f script/docker/docker-compose.yml logs -f iot-server
```

**后端改动后重新部署**：

```bash
cd iot-platform
mvn -Pprod -DskipTests clean package
docker compose -p devprojects -f script/docker/docker-compose.yml build iot-server
docker compose -p devprojects -f script/docker/docker-compose.yml up -d iot-server
```

**前端改动后重新部署**：

```bash
docker compose -p devprojects -f script/docker/docker-compose.yml build iot-web
docker compose -p devprojects -f script/docker/docker-compose.yml up -d iot-web
```

## 8. 故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `network devprojects_default ... could not be found` | 根编排未用 `-p devprojects` 启动 | 按 §1.1 指定项目名重启根编排 |
| `iot-nacos` unhealthy | Nacos 冷启动慢（约 3 分钟） | 编排已配 `start_period: 180s`，耐心等待；`docker logs iot-nacos` |
| `iot-kafka` unhealthy | KRaft 格式化/选主耗时 | 已配 `start_period: 30s`；检查 `docker logs iot-kafka` |
| `iot-emqx` unhealthy | 状态探测失败或启动中 | 等待并重试；确认 1883/18083 未被占用 |
| 后端连不上 Redis | 密码不匹配 | 确认 `ruoyi-redis` 以 `--requirepass 123456` 启动，且 `REDIS_PASSWORD=123456` |
| 后端连不上 Nacos | 默认未启用 Nacos（`NACOS_ENABLED:false`） | 本部署默认不启用；如需启用见下方说明 |
| 前端 200 但接口 404 | 后端未就绪或反代路径错误 | 检查 `iot-server` 状态与 Nginx `/prod-api` 反代 |
| SSE 连接被中断 | 代理缓冲/超时 | Nginx 已配 `proxy_buffering off`、`proxy_read_timeout 86400s`，确认未被外层代理覆盖 |
| `no space left` | ES/Kafka 数据卷占用过多 | `docker system prune`、清理数据卷 |

### 关于 Nacos

业务编排启动了 `iot-nacos`（鉴权开启，`nacos/123456`），但后端**默认不接入**（`NACOS_ENABLED:false`）。原因：Spring Cloud Alibaba 2025.1.0.0 官方适配 Spring Boot 4.0，而框架使用 Spring Boot 4.1.0，存在版本错位风险。产品 POM 将 Nacos 依赖置于独立 `profile`，默认不激活；需要接入时：

```bash
mvn -Pnacos -DskipTests clean package
```

并设置 `NACOS_ENABLED=true` 及对应的 `NACOS_USERNAME` / `NACOS_PASSWORD`。

## 10. Kubernetes 部署（Docker Desktop 内置 k8s）

整套服务也可部署到 **Docker Desktop 内置 Kubernetes**。该集群与 Docker 引擎共享镜像存储，本地 `docker build` 产出的镜像可被集群直接使用（`imagePullPolicy: IfNotPresent`），**无需私有镜像仓库**。

同一集群支持**多环境并存**：每个环境独立命名空间，前端入口使用不同 NodePort。

### 10.1 环境差异

| 维度 | dev（`iot-platform-dev`） | prod（`iot-platform-prod`） |
| --- | --- | --- |
| 前端入口 | NodePort **30080** | NodePort **30081** |
| 中间件 | 仅 postgres + redis | postgres / redis / elasticsearch / kafka / emqx / minio |
| 应用 | iot-server + iot-web | iot-server / iot-sba / iot-snailjob / iot-snailai / iot-web |
| ES / MQTT | 关闭（`EASY_ES_ENABLE=false`、`MQTT_CLIENT_ENABLED=false`） | 开启 |
| 控制台 Service | `iot-sba` / `iot-snailjob` / `iot-snailai` 仅创建占位 ClusterIP Service | 实际 Deployment + Service |
| 数据库初始化 | `db-init.sh` 自动执行 | `db-init.sh` 自动执行 |

> dev 的占位 Service 是为了让 Nginx upstream 的 DNS 可解析；访问 `/admin`、`/snail-job`、`/snail-ai` 会 502，属预期行为。

### 10.2 前置条件

1. **Docker Desktop → Settings → Kubernetes → Enable Kubernetes**
2. `kubectl config get-contexts` 能看到 `docker-desktop`
3. 业务镜像已构建（可由 GitHub Actions 完成，或手动 `docker build`）：
   `iot-platform/iot-platform-admin:1.0.0`、`iot-platform/monitor-admin:6.0.0`、`iot-platform/snailjob-server:2.0.2`、`iot-platform/snailai-server:1.1.1`、`iot-platform/plus-ui:1.0.0`

### 10.3 清单目录

```
iot-platform/script/k8s/
├── namespace.yaml              # 命名空间（部署时按环境渲染为 iot-platform-<env>）
├── secret.yaml                 # 数据库/Redis/MinIO/GITHUB_TOKEN 凭据
├── deploy-rbac.yaml            # 供平台「发布部署」更新 Deployment 的 RBAC
├── infrastructure/             # postgres / redis / elasticsearch / kafka / emqx / minio
├── apps/                       # iot-server / iot-sba / iot-snailjob / iot-snailai / iot-web
├── db-init-job.yaml            # 数据库初始化 Job
├── db-init.sh                  # 生成 SQL ConfigMap + 重建并等待 Job
├── deploy.sh                   # 一键部署（dev|prod）
└── destroy.sh                  # 删除目标环境命名空间
```

清单中的命名空间硬编码为 `iot-platform`；`deploy.sh` 会渲染到临时目录，替换为目标命名空间、把 `LoadBalancer` 改写为 `NodePort` 并注入端口，同时为 dev 创建占位 Service。

### 10.4 一键部署

```bash
cd d:/DevProjects/snail
bash iot-platform/script/k8s/deploy.sh dev     # 默认，命名空间 iot-platform-dev
bash iot-platform/script/k8s/deploy.sh prod    # 命名空间 iot-platform-prod
```

脚本顺序：

```
namespace → secret → deploy-rbac
          → infrastructure(apply)
          → 等待 postgres / redis rollout
          → db-init.sh（ConfigMap → Job → wait complete）
          → apps(apply)
          → 逐个等待 deployment rollout
```

### 10.5 数据库初始化（db-init）

`db-init.sh` 把 SQL 打成 4 个 ConfigMap，再删除并重建 Job `iot-db-init`（等待最多 600s）：

| ConfigMap | 内容 |
| --- | --- |
| `iot-sql-vector` | `init-vector.sql` |
| `iot-sql-base` | 框架基础脚本 `postgres_iot_vue.sql` |
| `iot-sql-framework` | `postgres_iot_workflow.sql`、`postgres_iot_job.sql`、`postgres_iot_ai.sql`、`snail_ai_schema_pgsql.sql` |
| `iot-sql-iot` | 产品 9 个业务脚本 |

Job 维护台账表：

```sql
iot_schema_history(file_name TEXT PRIMARY KEY, applied_at TIMESTAMP DEFAULT now())
```

- 基础/框架脚本：仅当 `sys_user` 不存在时执行一次；
- 业务脚本：按文件名只执行一次，顺序为
  `iot_platform` → `iot_permission` → `iot_sso` → `iot_pay` → `iot_ticket` → `iot_archive` → `iot_deploy` → `iot_cloud` → `iot_job`。

### 10.7 代码更新后的构建发布

k8s 中的镜像不会随源码变化自动更新，改完代码需**重新编译 → 重建镜像 → 重启 Deployment**。平台页面的「发布部署」只负责更新镜像/重启实例，不执行编译。

平台采用「**一个通用 Jenkins 流水线 + 每个应用登记构建配置**」：新增项目只要在「应用管理」里填好配置，无需在 Jenkins 中新建 Job。

#### 1. 添加项目（应用管理 → 新增）

| 字段 | 说明 | 示例（iot-server） |
| --- | --- | --- |
| 应用编码 | 唯一标识 | `iot-server` |
| 仓库地址 | Git 地址，或 Jenkins 容器内本地路径 | `/workspace/snail` |
| 分支 | Git 分支 | `main` |
| 构建目录 | 相对代码根目录，命令在此执行 | `.` |
| 构建命令 | 留空则由 Dockerfile 内部完成构建 | `mvn -B -DskipTests -f thirdparty/iot-vue-plus/pom.xml clean install && mvn -B -Pprod -DskipTests -f iot-platform/pom.xml clean package` |
| Dockerfile | 相对代码根目录 | `iot-platform/iot-platform-admin/Dockerfile` |
| 镜像名称 | **不含 tag**，构建时用版本号作 tag | `iot-platform/iot-platform-admin` |
| 工作负载 / 容器 | 目标 Deployment / 容器名 | `iot-server` / `iot-server` |

- 仓库地址以 `/` 开头时直接使用 Jenkins 挂载的工作区（如 `/workspace/snail`），本地未提交的改动同样生效；填 Git 地址则每次构建浅克隆到 `/workspace/repos/{应用编码}`。
- 前端 `iot-web` 的构建命令留空，由 `plus-ui/Dockerfile` 多阶段构建完成 `pnpm install + build:prod`。
- 依赖下载：Jenkins 挂载宿主 `~/.m2` 复用缓存，并通过 `script/jenkins/maven/settings.xml` 将 central 指向阿里云镜像。
- 任务记录清理：任务列表【删除】为逻辑删除（`del_flag=1`），需要 `iot:deploy:task:remove` 权限。

#### 2. 触发构建

- 【自动化部署】→ 工具栏【构建应用】→ 选择应用、填写版本/Tag、选择目标环境 → 确定；
- 【自动化部署】→【应用管理】→ 每行【构建】按钮。

两种入口都会弹出日志抽屉，实时显示 Jenkins 控制台输出。流水线阶段：准备代码 → 执行构建 → 归档 JAR → 构建镜像 → 部署到 Kubernetes，实际执行的是 [build-app.sh](file:///d:/DevProjects/snail/iot-platform/script/jenkins/build-app.sh)。

> 同一 Job 串行执行（`disableConcurrentBuilds`），前一个未结束时新构建进入队列。

#### 3. 本机手动构建

```powershell
# 后端
$env:MAVEN_OPTS='-Duser.home=D:\DevProjects\snail\.build-home -Dmaven.repo.local=C:\Users\ThinkPad\.m2\repository'
```

镜像 tag 复用 `:1.0.0` 时依赖 `imagePullPolicy: IfNotPresent` 使用本地镜像；若改为拉取远端仓库，需递增 tag 并同步修改 Deployment 与 `iot_deploy_app.artifact`。

不会自动执行，需手动导入：

```powershell

```

### 10.8 卸载

```bash

```

> 删除目标环境命名空间；默认 StorageClass 回收策略为 `Delete`，**PVC 数据会一并删除**。

### 10.9 与 Compose 的差异

| 维度 | Compose | Kubernetes |
| --- | --- | --- |
| 服务发现 | 服务名（`devprojects_default` 网络） | Service DNS（同名） |
| 数据库初始化 | `init-vector.sql` + 手动导入业务 SQL | `iot-db-init` Job 按台账幂等执行 |
| 前置依赖等待 | `depends_on` + `healthcheck` | `initContainer` + `readinessProbe` |
| 对外入口 | `ports: 80` | `Service type=NodePort`（dev 30080 / prod 30081） |
| 控制台 | 全部可用 | dev 下为占位 Service |

## 11. Jenkins 自动化构建部署

Jenkins 以容器方式运行，内置 JDK21 / Maven / Node22+pnpm / Docker CLI / kubectl，串联「构建后端 → 构建前端 → 构建镜像 → 部署到 k8s → 冒烟验证」全流程。

### 11.1 启动 Jenkins

```bash
cd d:/DevProjects/snail
docker compose -f iot-platform/script/jenkins/docker-compose.yml up -d --build
```

| 项 | 值 |
| --- | --- |
| 访问地址 | http://localhost:8090/ |
| 默认账号 | `admin / admin123` |
| 配置方式 | JCasC（[casc/jenkins.yaml](file:///d:/DevProjects/snail/iot-platform/script/jenkins/casc/jenkins.yaml)） |

容器挂载：

| 宿主 | 容器 | 用途 |
| --- | --- | --- |
| 仓库根 | `/workspace/snail` | Job 通过 `file:///workspace/snail` 本地克隆 |
| `/var/run/docker.sock` | `/var/run/docker.sock` | 复用宿主引擎构建镜像 |
| `%USERPROFILE%\.kube` | `/root/.kube`（只读） | kubectl 凭据 |
| `./casc` | `/var/jenkins_home/casc_configs` | JCasC 配置 |

### 11.2 预置内容

- 关闭安装向导，创建管理员 `admin/admin123`；
- 创建流水线 Job **`snail-iot-cicd`**，SCM 指向 `file:///workspace/snail`（分支 `main`），脚本路径 `iot-platform/Jenkinsfile`。

### 11.3 流水线阶段

| 阶段 | 动作 |
| --- | --- |
| 拉取代码 | 从 `/workspace/snail` 克隆到工作区 |
| 构建后端 | 框架 `mvn install` → 产品 `mvn -Pprod package` |
| 构建前端 | `pnpm install --frozen-lockfile` + `pnpm run build:prod` |
| 构建镜像 | `docker build` 出 5 个业务镜像 |
| 部署到 Kubernetes | 执行 `script/k8s/deploy.sh dev` |
| 冒烟验证 | 校验 `iot-web` 页面可访问，且后端服务端口连通 |

### 11.4 注意事项

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Permission denied` 操作 docker.sock | 宿主 socket 属组不匹配 | 编排已设 `user: root` |
| kubectl 连接 `127.0.0.1:6443` 超时 | 容器内回环地址指向自身 | 流水线改写为 `kubernetes.docker.internal:6443` |
| `dubious ownership` | bind-mount 仓库属主不一致 | 镜像内已配置 `safe.directory '*'` |
| `Non-resolvable parent POM` | 未先安装框架底座 | 流水线已内置 install 步骤 |
| dev 冒烟失败 | dev 为精简栈，控制台服务无 Pod | 以 `iot-web` + `iot-server` 为准 |

## 12. GitHub Actions 自动化部署（推荐）

> 与第 11 节 Jenkins 方案**替代/并行**，两者都通过 `script/k8s/deploy.sh <env>` 部署。

### 12.1 方案概览

| 环境 | 命名空间 | 前端入口 | 触发方式 | 工作流 |
| --- | --- | --- | --- | --- |
| dev | `iot-platform-dev` | http://localhost:30080/ | **推送 `main` 自动部署** + 手动 | [deploy-dev.yml](file:///d:/DevProjects/snail/.github/workflows/deploy-dev.yml) |
| prod | `iot-platform-prod` | http://localhost:30081/ | 仅**手动 Run workflow**（可填版本号） | [release-prod.yml](file:///d:/DevProjects/snail/.github/workflows/release-prod.yml) |

代码来源：`https://github.com/ksf127/Snail-IoT.git`（公开仓库，`actions/checkout` 无需额外凭据）。

流水线阶段：

```
拉取代码 → 构建后端(thirdparty → iot-platform) → 构建前端(plus-ui)
        → 构建 5 个镜像 → deploy.sh <env> 部署到 k8s → 冒烟验证
```

> 镜像 tag 在两条工作流中固定为 `1.0.0`；`release-prod.yml` 输入的版本号目前仅作发布记录，不改变镜像 tag。

### 12.2 前置条件：self-hosted runner

部署目标是**本机 Docker Desktop Kubernetes**，云端 runner 无法访问，需在本机注册 GitHub self-hosted runner：

1. `https://github.com/ksf127/Snail-IoT` → **Settings → Actions → Runners → New self-hosted runner**，选择 **Windows**；
2. 配置标签 `snail-iot`（工作流使用 `runs-on: [self-hosted, snail-iot]`）：

```powershell
./config.cmd --url https://github.com/ksf127/Snail-IoT --token <页面给出的 token> --labels snail-iot
./run.cmd      # 前台运行；或用 ./svc.sh install 注册为服务
```

3. runner 机器需具备：Git for Windows（`shell: bash`）、JDK 21、Maven 3.9+、Node 22 + pnpm 10、Docker Desktop（启用 Kubernetes）+ kubectl（`docker-desktop` 上下文）。

### 12.3 触发方式

- **开发环境（自动）**：向 `main` 推送涉及 `iot-platform/**`、`thirdparty/**`、`init-vector.sql` 或工作流文件的提交；
- **开发环境（手动）**：Actions → **部署开发环境** → Run workflow；
- **生产环境（手动）**：Actions → **发布生产环境** → Run workflow。

### 12.4 发布登记

`iot_deploy_app` / `iot_deploy_env` 两张登记表已内置本项目与 dev/prod 环境（见 `iot-platform/script/sql/postgres/iot_deploy.sql`），前端「自动化部署」的发布弹窗下拉即读取该数据。

### 12.5 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 一直 `Waiting for a runner` | 无匹配 `snail-iot` 的在线 runner | 确认 runner 已启动且标签正确 |
| `bash: command not found` | 未安装 Git for Windows | 安装后重试 |
| `mvn` / `pnpm` not found | runner 缺工具 | 按 §12.2 安装 |
| `kubectl` 连不上集群 | 未启用 Kubernetes 或上下文不对 | Docker Desktop 启用 k8s |
| prod 未部署 | prod 为手动触发 | 到 Actions 手动 Run workflow |
| 冒烟测试检查控制台失败 | dev 精简栈下控制台为占位 Service | 以 `iot-web` + `iot-server` 为准 |
